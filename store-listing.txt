Kepuli-TV — Chrome Web Store listing copy
=========================================
The store page does not support Markdown. These texts are deliberately plain
and can be copied as they are. English is the language to choose: it is what
the listing is written in, and what the player falls back to for anyone whose
browser it does not speak.

The store's reviewers read the description under the "Spam and placement in
the Store" policy (violation reference Yellow Argon). The first submission was
rejected for a list of file extensions in the detailed description. What the
policy forbids, and what this text therefore avoids:
  • lists of keywords, file types, brands or sites: write sentences, and name
    a format only where the sentence needs it, at most a couple per sentence
  • lists of countries or regions: one example at most
  • any one keyword used five times or more (the Spam FAQ says "under 5",
    and counts the primary purpose word too); the audit below every word
    with a meaning stays at four or fewer
  • anonymous testimonials, superlatives, and mentions of competing extensions


--- PUBLISHING A NEW VERSION -----------------------------------------------
Most of this file is written once and left alone. What a release actually
touches in the dashboard, and what it does not:

ALWAYS
  • Package (Package → Upload new package): kepuli-tv-chrome-<version>.zip
    from node dev/package.mjs --zip — never the firefox one beside it. Chrome
    accepts the Firefox package without a word. Up to 1.2.5 its manifest had
    background.scripts alone, which Chrome ignores: no service worker ran,
    and the toolbar button did nothing (1.2.1 and 1.2.5 went out that way).
    Since 1.2.6 the Firefox manifest carries background.service_worker too,
    so a mix-up no longer breaks the extension, but the store would still
    show Firefox's keys as unrecognised. Chrome takes the version from the
    manifest; there is no version field to type and no release-notes field
    at all.

AFTER THE REVIEW, EVERY TIME
  • Read the manifest of the package the store now serves, with the
    commands under "Publishing to the stores" in README.md. It must show
    the new version and "service_worker", and no "gecko". "gecko" means the
    Firefox zip was uploaded: publish the next version with the Chrome zip.
  • Install from the store on another machine and click the toolbar button:
    the player must open.

WHEN THE PLAYER LOOKS DIFFERENT
  • Screenshots (Store listing → Graphic assets): all five, from
    node dev/store-screenshots.mjs. Delete the old ones first — the store
    keeps what you do not replace, and a stale shot beside a fresh one is
    worse than either.
  • Detailed description, if a section of it has stopped being true.

ONLY WHEN THE MANIFEST CHANGES
  • Name and short description — read from _locales/ through the manifest,
    in every language, so they change only when store/listings/ does.
  • Permission justifications and the single-purpose text — only if
    permissions, host permissions or the single purpose changed. Adding a
    permission puts the submission into a longer review; changing neither
    keeps it in the ordinary queue.
  • Data usage checkboxes and certifications — only if what the extension
    receives from the user changes.

RARELY
  • Category, language, homepage, support URL, privacy policy URL, test
    instructions: leave them unless the thing they describe has moved.

--- THE TEXTS, IN THIRTEEN LANGUAGES ---------------------------------------
The name, the short description and the detailed description live in
store/listings/<locale>.txt, one file per language, and nowhere else. The
English one is store/listings/en.txt. Run

  node dev/listings.mjs

after editing any of them. The name is the brand, "Kepuli-TV – IPTV Player" in
every language, never translated. It checks each against the store's limits and the
keyword policy above (name 45 characters, short description 132, detailed
16,000, no word of five letters or more — nor IPTV, MKV and the like — five
times or more), writes _locales/<locale>/messages.json, which is where both
stores read the name and the short description from, and writes
dist/listings/<locale>.txt, the same texts with each paragraph on one line,
ready to paste. Paste from there, not from store/listings/: that is wrapped
at 78 columns for reading, and the stores keep every line break.
dev/package.mjs refuses to build when _locales/ is out of step.

The locale codes are the Chrome Web Store's: pt_BR, and "no" for Norwegian.
Firefox looks for Norwegian Bokmål under nb_NO, and the Firefox package
renames the folder (dev/package.mjs).


SETTING THE LANGUAGES IN THE CHROME WEB STORE
  1. Upload the package that carries _locales/ (Package → Upload new
     package). From then on the store shows the name and the short
     description from _locales/ in each reader's language by itself; there
     is no field to type them into, in any language.
  2. Store listing → the language menu at the top right of the form (it
     says English). Pick a language — the menu offers the locales the
     package has.
  3. Paste "DETAILED DESCRIPTION" from dist/listings/<locale>.txt into
     Description. Screenshots and the promo tiles may be left empty: a
     language without its own falls back to the English ones.
  4. Repeat for every language, then Submit for review. The descriptions go
     through the review with the package.

--- THE PRIVACY PRACTICES TAB ----------------------------------------------
The fields below are written for the reviewer. The character limits are 1,000
per field; all of them fit.


SINGLE PURPOSE DESCRIPTION (815 characters)
-------------------------------------------
Kepuli-TV does one thing: it plays back the user's own IPTV subscription in the browser.

The user enters the address and credentials of an Xtream Codes server they already pay for. The extension lists that account's live channels, movies and series and plays them in its own tab, together with the programme guide the server provides.

The extension ships no content, no channel list and no account of its own; it is useless without an account the user brings. It has no content scripts and never touches the pages the user browses - clicking the toolbar icon opens the extension's own tab and nothing else. Every feature serves that single purpose: fetching the account's catalogue, remuxing MKV to fMP4 so Chrome can play it, decoding AC-3/E-AC-3/DTS audio, showing subtitles, and remembering playback positions.


STORAGE JUSTIFICATION (855 characters)
--------------------------------------
chrome.storage.local holds only what the player cannot work without:

1) The connection the user configures - their own IPTV server address, port, username and password - so the credentials are not retyped every time the player tab is opened.
2) Playback preferences: interface language, subtitle language, look and size, and stream mode.
3) The user's own lists: favourites, recently watched, and the resume position per movie and episode.

All of it is written by the user's own actions inside the extension's own tab, stays on the device, and is never transmitted anywhere - the extension has no backend and no analytics. Without this permission the user would have to re-enter their server address and credentials on every launch, and no favourite, history entry or resume position could survive a page reload.


UNLIMITEDSTORAGE JUSTIFICATION (688 characters)
-----------------------------------------------
The catalogue returned by the user's own IPTV server is cached in IndexedDB so it is not re-downloaded on every launch. These catalogues are large: tens of megabytes of JSON for channels, movies and series, and programme guide data per channel. That routinely exceeds the default quota Chrome grants an extension. When the quota is hit, cache writes fail and the user waits through a full re-download of a multi-megabyte listing on every navigation, which makes the extension unusable on normal IPTV accounts.

No personal data is stored under this permission - only a copy of the listing the user's own server returned. The cache can be cleared from the extension's settings at any time.


HOST PERMISSION JUSTIFICATION (686 characters)
----------------------------------------------
This field appears only if the store asks about host permissions. The manifest
declares optional_host_permissions rather than host_permissions, so the field
may not appear at all.

The extension does not request host access at install time. http://*/* and https://*/* are declared under optional_host_permissions only, and Chrome asks for the permission at runtime - for the single origin the user typed - the first time they save their own server address.

The permission is needed because an IPTV server can be at any address and that address is unknowable before installation; the user brings it. Access is used solely for fetch/XHR against that server: the player_api.php endpoint, and the HLS/TS segment requests made by hls.js and mpegts.js. The extension has no content scripts, injects nothing into web pages, and reads no data from any site the user browses.


ARE YOU USING REMOTE CODE?
--------------------------
The choice: "No, I am not using Remote code".

Justification (706 characters), if the field is open:

No remote code is used. Every script and binary the extension executes ships inside the package: mpegts.js and hls.js under vendor/, and an audio decoder compiled from FFmpeg to WebAssembly at vendor/ffaudio/, loaded with fetch() from the extension's own chrome-extension:// path. There are no <script> tags referencing external files, no remote module imports, no eval() and no new Function().

The manifest CSP is "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'". The 'wasm-unsafe-eval' keyword is required only to instantiate that packaged .wasm file; no remote origin appears in script-src. Network requests fetch media and catalogue data from the IPTV server the user configures - never code.


DATA USAGE — THE CHECKBOXES
---------------------------
Tick:
  [x] Authentication information

Leave every other box unticked:
  [ ] Personally identifiable information — no name, e-mail address or
      identity number is asked for
  [ ] Health information
  [ ] Financial and payment information — the extension handles no payments
  [ ] Personal communications
  [ ] Location — no geolocation; the user's own server sees their IP, but that
      is the provider's traffic and not something the extension collects
  [ ] Web history — no content scripts, no access to browsing history
  [ ] User activity — favourites, history and resume positions stay on the
      device and are sent nowhere
  [ ] Website content — the extension does not read the contents of the pages
      being browsed

Why Authentication information is ticked even though nothing is sent to the
developer: the user enters their IPTV credentials into the extension, and in
the manner of the Xtream Codes API those are passed in the request URL to the
user's own server. The store's definition of "user data" covers data received
from the user, and asking for credentials without the tick is a known
rejection reason ("incomplete data disclosure"). The tick is not a problem: all
three certifications (not sold, not used outside the single purpose, not used
for creditworthiness) hold true, and the privacy policy states that the
credentials stay on the device and travel only to the user's own server.

Certifications: tick all three.
